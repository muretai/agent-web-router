# Agent Web Router v0

**How an agent chooses its way into a website, when it may follow a handoff, and what it
refuses to take from the site: an identity, an order, or a second try.**

Status: **Draft.** Version 0. Every requirement below is decided by what the agent can
observe over HTTP, and each is stated with the test that checks it. Requirements that no test
in this repository exercises are not stated as requirements.
Editor: Muretai. Licence: MIT, the same as the reference implementation.

---

## 1. What this specifies

A website may offer an agent up to three **ways in**:

- **page** — tools registered in the page under the WebMCP API, declarative
  (`<form toolname tooldescription>`) or imperative (`document.modelContext`). They execute in
  a browser, as that browser's session.
- **mcp** — an MCP server the site declares at `/.well-known/mcp.json`.
- **card** — an Agent Card at `/.well-known/agent-card.json` naming a door (`url`) and an
  identity (`did`), where one signed A2A `message/send` is answered in the same request.
  The door is whoever the card names — any implementation of that contract, not one vendor.

A **router** is the visitor-side component that discovers which ways an origin offers,
orders them by what the visitor has on hand, and decides whether a **handoff** — a
continuation named inside a tool result — may be followed.

This document specifies the router. It does not specify any of the three ways; each has its
own specification. It does not specify how a visitor obtains or stores a key.

## 2. Terminology

The key words MUST, MUST NOT, SHOULD and MAY are to be interpreted as described in BCP 14
(RFC 2119, RFC 8174) when, and only when, they appear in all capitals.

**Origin** — the scheme, host and port the visitor dialled.
**On hand** — four booleans the visitor states about itself: `person` (a human is present in
a browser tab on this site), `browser` (the visitor can run a browser itself), `token` (the
visitor holds a credential for the site's MCP server), `key` (the visitor holds an Ed25519
signing key, i.e. a `did:key`).
**Handoff** — an object in a tool result naming where the interaction continues (§5).

## 3. Probing

**AWR-1.** A probe accepts only an absolute HTTP or HTTPS URL and MUST reject every other
scheme before fetching. It MUST use only `GET`; it MUST NOT `POST`, execute page script, or
open a browser. *(test: "the command line refuses bad input with exit 1 and never POSTs")*

**AWR-1a.** A response longer than the byte cap MUST be abandoned at the cap: the finding is
recorded and the remainder of the body is never read. An endless body is a finding, not a
hang. *(test: "ATTACK: a body that never ends is abandoned at the cap — a finding, not a
crash")*

**AWR-2.** A probe MUST request `/.well-known/agent-card.json` and MAY fall back to
`/.well-known/agent.json`. It MUST request `/.well-known/agent-card.sig.json` when a card was
found. *(tests: "probe finds the card…", "the legacy /.well-known/agent.json is read…")*

**AWR-3.** A probe MAY request `/.well-known/mcp.json` and MAY read the front page's HTML to
list declarative tools (WebMCP `<form toolname tooldescription>`; VOIX `<tool name
description>`). A probe MUST NOT claim an imperative tool list it did not obtain by
executing the page; it MAY report a hint. *(tests: "declarative WebMCP tools are read…", "an
MCP server card is a route only…", "VOIX <tool> elements are listed…")* HTML comments are
not part of the parsed document and MUST NOT create declarative tools. *(test: "commented-out
declarative tools are not reported…")*

**AWR-3a.** A probe MAY read other signposts a site publishes for agents — `/robots.txt`,
`/llms.txt` and `/llms-full.txt`, a Markdown edition of the front page on
`Accept: text/markdown`, JSON-LD `@type`s in the front page, a `Link` header on the front
page — and report them.
A signpost MUST NOT create a route. *(test: "signposts are reported in one place and never
become a route")*

**AWR-3b.** A probe MUST finish within a wall-clock deadline shared by all of its requests
(the reference implementation defaults to 30 s). A request not started before the deadline
MUST be skipped and recorded, once; a skipped step reports through the normal absent-way
reasons and MUST NOT be raised as an error. *(test: "a black-holing origin cannot hold a
probe past the deadline; steps not reached are notes, not a crash")*

## 4. The card route

**AWR-4.** A card served from an origin other than the one dialled MUST be ignored. *(test:
"ATTACK: a card served through a redirect to another origin is discarded, and the probe says
so")*

**AWR-5.** The card route MUST be excluded when the card's `url` does not name the dialled
origin. *(test: "ATTACK: a card whose url names another origin…")*

**AWR-6.** When a signature envelope is present and does not verify under the card's own
`did`, or verifies but differs from the plain card, the card route MUST be excluded. A
present-but-invalid signature—including a successful HTTP response that exceeds the byte
cap or is interrupted while its body is read—MUST NOT be treated as an absent one. The
envelope version MUST be exactly `1`; an unknown or relabelled version fails closed. *(tests:
"ATTACK: a signed card signed by another key…", "ATTACK: a signed card that differs…",
"ATTACK: relabelling a v1 card signature…", "ATTACK: an oversized signature response…",
"ATTACK: an interrupted HTTP 200 signature response…")*

**AWR-7.** When no signature envelope is served, the card route MAY be offered; the
implementation SHOULD say so. *(test: "the legacy /.well-known/agent.json is read…")*

**AWR-7a.** When the dialled origin serves `/.well-known/did-configuration.json` and the card
names a `did`, an implementation SHOULD verify the Domain Linkage Credential rather than only
read the naming. A compact-JWS `linked_dids` entry verifies when, and only when: every
segment is unpadded base64url (a padded or standard-alphabet spelling is refused, not
repaired); the header's `alg` is `EdDSA`; `iss`, `sub` and `vc.credentialSubject.id` are all
the card's `did`; `vc.type` includes `DomainLinkageCredential`; `vc.credentialSubject.origin`,
canonicalized, equals the dialled origin; `exp` is present as an integer — a domain is
leased, not owned — and the time of checking sits within `[nbf, exp]`; and the Ed25519
signature verifies over the ASCII text of the first two segments under the key the `did`
encodes. Each failure MUST be reported by name. The verdict is reported beside the card and
MUST NOT create or remove a route. Only the dialled origin's document is read: a router never
fetches another domain's did-configuration to prove this one. *(tests: `vectors.test.mjs`
"the Domain Linkage credential verifies byte-for-byte…" and "…refused for the right
reason…"; "the domain linkage proof is verified, not just read…")*

The signature envelope is `{v:1, typ:"agentcard", card, ts, sig}` with `sig` the Ed25519
signature over the canonical JSON of `{card, ts, typ, v}` — keys sorted by code point,
separators `,` and `:`, non-ASCII literal, UTF-8 — under the key the card's `did` encodes.

## 5. Ordering

The order is the **site's** to design; the router's own order (AWR-8, AWR-9) is what applies
when the site says nothing. The site says it in its card, because the card is the origin's
own statement — signed when the site signs it — and a page is not.

**AWR-8.** Unless the card declares otherwise (AWR-17), when `person` is on hand and the page
declares tools, the page MUST be first. *(test: "a person in the tab goes to the page
first…")*

**AWR-9.** Unless the card declares otherwise (AWR-17), when `person` is not on hand, the
card route (when not excluded) MUST precede the others. *(same test)*

**AWR-17.** A card MAY declare its order at `agentEntry.prefer`: an array whose entries are
a kind (`"page"`, `"card"`, `"mcp"`) or `{ "kind", "when" }` with `when` one of `person`,
`alone`, `key`, `no-key`, `token`, `browser`, read against what the visitor has on hand.
When the card is usable under §4, the router MUST place the declared entries whose `when`
holds, in the declared order, ahead of its own order. *(tests: "a site can put its server
ahead of its door…", "a site can say read on the page first if you have no key…")*

**AWR-18.** A declaration only re-orders what is on offer. It MUST NOT add a route excluded
under AWR-5, AWR-6, AWR-10, AWR-10a or AWR-11. *(test: "ATTACK: a site's order cannot add a route the
rules exclude")*

**AWR-19.** A declaration in a card excluded under §4 MUST be ignored. Entries of unknown
kind or unknown condition MUST be dropped, never guessed. *(tests: "ATTACK: the order declared
by a card that fails its signature is ignored", "an unknown kind or condition… is dropped")*

**AWR-10.** The mcp route MUST NOT be offered without `token` on hand unless the server card
states that no credential is required. *(test: "an MCP server card is a route only…")*

**AWR-10a.** The mcp route MUST be excluded when the server card's declared endpoint does not
name the dialled origin — `/.well-known/mcp.json` is the origin's statement about itself, and
an endpoint elsewhere is not this site's server. A server card served from an origin other
than the one dialled MUST be ignored, as a card is under AWR-4. Neither a token on hand nor a
declared open access changes this. *(test: "ATTACK: an mcp endpoint on another origin is
excluded, not dialled")*

**AWR-11.** The page route MUST NOT be offered to a visitor without `person` or `browser` on
hand. *(test: "a person in the tab goes to the page first…")*

**AWR-11a.** When `/robots.txt` exists and its `*` group disallows `/`, the page route
MUST NOT be offered to a visitor without `person` on hand. A visitor with `person` on hand is
not a crawler and is unaffected; the card route is unaffected. *(test: "a robots.txt that
closes the front page to everyone excludes the HEADLESS page route…")* When multiple groups
match the same user agent, their rules MUST be combined before applying the longest-match
rule (RFC 9309). *(test: "duplicate matching robots groups are combined before routing")*

**AWR-12.** Every way MUST appear in exactly one of `routes` and `excluded`, with a reason
when excluded. *(test: "a site with nothing offers no route…")*

## 6. Handoff

A handoff is carried in a tool result under `_meta.handoff` (or top-level `handoff`):

```
{ "v": 1, "next": [ entry, … ] }
entry := { "kind": "dm",  "to": did, "message"?, "connect"? }
       | { "kind": "a2a", "to"?: did, "endpoint"?: url, "card"?: url, "message"? }
       | { "kind": "ui",  "url": url, "why"? }
       | { "kind": "mcp", "server": url }
```

A legacy `{ "muretai": { "v":1, "action":"dm", "to", "connect"?, "suggested_message"? } }`
MUST be read as a single `dm` entry.

**AWR-13.** The handoff version MUST be present and equal to `1`; an unknown or missing
version is not interpreted using v1 semantics. An entry of unknown `kind`, or lacking its
required field, MUST be dropped. For `a2a`, any one of `to`, `endpoint`, or `card` is
sufficient, so a card-only entry is valid. A result with no valid entry MUST be reported as
carrying no handoff. *(tests: "a malformed handoff is nothing to follow", "an unknown or
missing handoff version is nothing to follow", "an a2a handoff may name only its Agent Card
URL")*

**AWR-14.** An entry naming a `to` MUST be refused unless `to` equals the `did` of a card the
origin serves that is not excluded under §4. The decision receives the complete card probe
record; a detached raw card, which no longer carries the origin and signature verdicts,
cannot vouch for a handoff, nor can a usable record produced by probing a different origin.
*(tests: "a handoff to the DID the card names…", "ATTACK: a handoff is not vouched for by a
card that fails its signature", "checkHandoff requires the probe card record…", "a usable
card record from another origin cannot authorize…")*

**AWR-15.** An entry naming no `to` and any URL off the dialled origin MUST be refused. A
card record produced by probing another origin does not extend that boundary. *(tests: "a ui
continuation on the origin is accepted but flagged…", "a usable card record from another
origin cannot authorize…")*

**AWR-16.** A `ui` entry MUST NOT be opened without `person` on hand; an implementation MUST
mark it as requiring a person. *(same test)*

## 7. The knock

A router MAY complete the card route by sending one signed message to the door.

**AWR-20.** A knock MUST be sent only when the card route is offered under §4 — never after
a refusal. A substituted card, an off-origin `url`, or a failed signature means no POST at
all. *(test: "ATTACK: a substituted card means no knock at all")*

**AWR-21.** A knock MUST be signed with a key the caller supplied. A router MUST NOT mint a
key. Without a key it MUST send nothing and MAY show the door's own instructions. *(test:
"knock without a key sends nothing…")*

**AWR-22.** The message is an A2A `message/send` whose `metadata.sig` is the Ed25519
signature over the canonical JSON of exactly `{contextId, from, messageId, text, timestamp,
to}` (keys sorted by code point, separators `,` and `:`, non-ASCII literal, UTF-8; `contextId`
is JSON `null` when absent; `timestamp` is an integer epoch), base64 standard with padding.
The bytes MUST match the Agent Entry conformance vectors. *(tests: `vectors.test.mjs`,
"canonical JSON sorts object keys by Unicode code point…")*

**AWR-23.** The POST MUST go to the endpoint the card (or its signed-envelope scheme) names,
and that endpoint MUST be on the dialled origin; the recipient MUST be the card's `did`.
*(test: "knock: one signed message at the door…")*

**AWR-24.** A reply MUST be verified before it is shown as the door's: `metadata.from` MUST
equal the DID the card names (never the reply's own `from` taken as a label), `metadata.to`
MUST be the visitor's DID, `metadata.timestamp` MUST be within 300 s, and the signature MUST
verify over the reply's own six fields, including a non-empty `messageId`. Each failure MUST
be reported by name. An unverified reply's body MUST be withheld from both structured and
human-readable output. A JSON-RPC error from the door is an answer and MUST be shown, not
raised. *(tests: "ATTACK: a reply signed by another key…" ×2, "ATTACK: a stale reply…",
"ATTACK: a signed reply missing messageId…", "the door's refusal is an answer…")*

## 7b. Conduct

Three rules that hold across §3–§7. Each exists because the opposite is what an injected
instruction, a rewritten page or an impatient loop would do, and each is stated with the test
that attempts the opposite.

**AWR-25.** The visitor's identity comes from the caller. A router MUST derive `from` from the
key the caller supplied, and MUST NOT take a key, a DID or a display name for the visitor
from anything fetched from the site — its card, its page, a tool result or a handoff. Fields
such as `from`, `as` or `agent_name` in those places MUST be ignored. *(test: "ATTACK: a site
that says who the visitor should be is ignored — identity comes from the key, never from the
site")*

> With `did:key` the identity IS the key, so a site cannot hand the visitor one; the rule
> makes that hold at the seams where a name could still be copied — the contract the probe
> prints, and the handoff entries it accepts.

**AWR-26.** A tool result is data. A router MUST consume from a tool result only the handoff
envelope at `_meta.handoff` (or top-level `handoff`, or the legacy `muretai` key). Text in
`content[]`, an object under `structuredContent`, or any other field MUST NOT create, add or
re-order a route or a handoff entry, whatever it says and whatever the tool's annotations say
about it — the absence of an `untrustedContentHint` is not trust. *(test: "a tool result's
text is data: a handoff written in prose or under structuredContent is not followed")*

**AWR-27.** A refusal is final for the call. A `knock` MUST make exactly one POST. When the
door answers HTTP 429 or 503, or a JSON-RPC error, the router MUST return that answer to the
caller — with `Retry-After` surfaced as `retryAfter` in whole seconds when the door sent one —
and MUST NOT re-send the same message or a fresh one. A signed-looking `result` on a non-2xx
HTTP response remains a refusal and MUST NOT be shown as verified. The response body MUST be
abandoned at its byte cap rather than read until timeout. Status and `Retry-After` remain
observable even if reading the refusal body is interrupted. *(tests: "ATTACK: the door's
refusal is final for the call…", "ATTACK: a signed result on HTTP 429 or 503…", "ATTACK: an
endless knock response is abandoned at the cap", "an interrupted refusal body still
surfaces HTTP status and Retry-After")*

> Re-sending the same signed message is a replay by construction; re-sending a fresh one
> inside the window is precisely what the door asked the caller not to do. Whether to come
> back later is the caller's decision, made with the door's own number in hand.

## 7a. Out of scope

Minting a key and where it is stored are not specified here. Browsing the page is not
specified here: the page route is handed to whatever browser the visitor has.

## 8. Conformance

An implementation conforms when the tests named above pass against it. The reference
implementation is `agent-web-router.mjs` in this repository; `npm test` runs the suite
against a local site fixture that signs its own card with its own independent canonicalizer.
