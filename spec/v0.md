# Agent Web Router v0

**How an agent chooses its way into a website, and when it may follow a handoff.**

Status: **Draft.** Version 0. Every requirement below is decided by what the agent can
observe over HTTP, and each is stated with the test that checks it. Requirements that no test
in this repository exercises are not stated as requirements.
Editor: Muretai. Licence: MIT, the same as the reference implementation.

---

## 1. What this specifies

A website may offer an agent up to three **ways in**:

- **page** — tools registered in the page under the WebMCP API, declarative
  (`<form toolname tooldescription>`) or imperative (`document.modelContext`). They execute in
  a browser, as that browser's session.
- **mcp** — an MCP server the site declares at `/.well-known/mcp.json`.
- **card** — an Agent Card at `/.well-known/agent-card.json` naming a door (`url`) and an
  identity (`did`), where one signed message is answered in the same request (Agent Entry).

A **router** is the visitor-side component that discovers which ways an origin offers,
orders them by what the visitor has on hand, and decides whether a **handoff** — a
continuation named inside a tool result — may be followed.

This document specifies the router. It does not specify any of the three ways; each has its
own specification. It does not specify how a visitor obtains or stores a key.

## 2. Terminology

The key words MUST, MUST NOT, SHOULD and MAY are to be interpreted as described in BCP 14
(RFC 2119, RFC 8174) when, and only when, they appear in all capitals.

**Origin** — the scheme, host and port the visitor dialled.
**On hand** — four booleans the visitor states about itself: `person` (a human is present in
a browser tab on this site), `browser` (the visitor can run a browser itself), `token` (the
visitor holds a credential for the site's MCP server), `key` (the visitor holds an Ed25519
signing key, i.e. a `did:key`).
**Handoff** — an object in a tool result naming where the interaction continues (§5).

## 3. Probing

**AWR-1.** A probe MUST use only `GET`. It MUST NOT `POST`, execute page script, or open a
browser. *(test: "the command line refuses bad input with exit 1 and never POSTs")*

**AWR-2.** A probe MUST request `/.well-known/agent-card.json` and MAY fall back to
`/.well-known/agent.json`. It MUST request `/.well-known/agent-card.sig.json` when a card was
found. *(tests: "probe finds the card…", "the legacy /.well-known/agent.json is read…")*

**AWR-3.** A probe MAY request `/.well-known/mcp.json` and MAY read the front page's HTML to
list declarative tools (WebMCP `<form toolname tooldescription>`; VOIX `<tool name
description>`). A probe MUST NOT claim an imperative tool list it did not obtain by
executing the page; it MAY report a hint. *(tests: "declarative WebMCP tools are read…", "an
MCP server card is a route only…", "VOIX <tool> elements are listed…")*

**AWR-3a.** A probe MAY read other signposts a site publishes for agents — `/robots.txt`,
`/llms.txt` and `/llms-full.txt`, a Markdown edition of the front page on
`Accept: text/markdown`, JSON-LD `@type`s in the front page, a `Link` header on the front
page — and report them.
A signpost MUST NOT create a route. *(test: "signposts are reported in one place and never
become a route")*

## 4. The card route

**AWR-4.** A card served from an origin other than the one dialled MUST be ignored.

**AWR-5.** The card route MUST be excluded when the card's `url` does not name the dialled
origin. *(test: "ATTACK: a card whose url names another origin…")*

**AWR-6.** When a signature envelope is present and does not verify under the card's own
`did`, or verifies but differs from the plain card, the card route MUST be excluded. A
present-but-invalid signature MUST NOT be treated as an absent one. *(tests: "ATTACK: a
signed card signed by another key…", "ATTACK: a signed card that differs…")*

**AWR-7.** When no signature envelope is served, the card route MAY be offered; the
implementation SHOULD say so. *(test: "the legacy /.well-known/agent.json is read…")*

The signature envelope is `{v:1, typ:"agentcard", card, ts, sig}` with `sig` the Ed25519
signature over the canonical JSON of `{card, ts, typ, v}` — keys sorted by code point,
separators `,` and `:`, non-ASCII literal, UTF-8 — under the key the card's `did` encodes.

## 5. Ordering

The order is the **site's** to design; the router's own order (AWR-8, AWR-9) is what applies
when the site says nothing. The site says it in its card, because the card is the origin's
own statement — signed when the site signs it — and a page is not.

**AWR-8.** Unless the card declares otherwise (AWR-17), when `person` is on hand and the page
declares tools, the page MUST be first. *(test: "a person in the tab goes to the page
first…")*

**AWR-9.** Unless the card declares otherwise (AWR-17), when `person` is not on hand, the
card route (when not excluded) MUST precede the others. *(same test)*

**AWR-17.** A card MAY declare its order at `agentEntry.prefer`: an array whose entries are
a kind (`"page"`, `"card"`, `"mcp"`) or `{ "kind", "when" }` with `when` one of `person`,
`alone`, `key`, `no-key`, `token`, `browser`, read against what the visitor has on hand.
When the card is usable under §4, the router MUST place the declared entries whose `when`
holds, in the declared order, ahead of its own order. *(tests: "a site can put its server
ahead of its door…", "a site can say read on the page first if you have no key…")*

**AWR-18.** A declaration only re-orders what is on offer. It MUST NOT add a route excluded
under AWR-5, AWR-6, AWR-10 or AWR-11. *(test: "ATTACK: a site's order cannot add a route the
rules exclude")*

**AWR-19.** A declaration in a card excluded under §4 MUST be ignored. Entries of unknown
kind or unknown condition MUST be dropped, never guessed. *(tests: "ATTACK: the order declared
by a card that fails its signature is ignored", "an unknown kind or condition… is dropped")*

**AWR-10.** The mcp route MUST NOT be offered without `token` on hand unless the server card
states that no credential is required. *(test: "an MCP server card is a route only…")*

**AWR-11.** The page route MUST NOT be offered to a visitor without `person` or `browser` on
hand. *(test: "a person in the tab goes to the page first…")*

**AWR-11a.** When `/robots.txt` exists and its `*` group disallows `/`, the page route
MUST NOT be offered to a visitor without `person` on hand. A visitor with `person` on hand is
not a crawler and is unaffected; the card route is unaffected. *(test: "a robots.txt that
closes the front page to everyone excludes the HEADLESS page route…")*

**AWR-12.** Every way MUST appear in exactly one of `routes` and `excluded`, with a reason
when excluded. *(test: "a site with nothing offers no route…")*

## 6. Handoff

A handoff is carried in a tool result under `_meta.handoff` (or top-level `handoff`):

```
{ "v": 1, "next": [ entry, … ] }
entry := { "kind": "dm",  "to": did, "message"?, "connect"? }
       | { "kind": "a2a", "to"?: did, "endpoint"?: url, "card"?: url, "message"? }
       | { "kind": "ui",  "url": url, "why"? }
       | { "kind": "mcp", "server": url }
```

A legacy `{ "muretai": { "v":1, "action":"dm", "to", "connect"?, "suggested_message"? } }`
MUST be read as a single `dm` entry.

**AWR-13.** An entry of unknown `kind`, or lacking its required field, MUST be dropped. A
result with no valid entry MUST be reported as carrying no handoff. *(test: "a malformed
handoff is nothing to follow")*

**AWR-14.** An entry naming a `to` MUST be refused unless `to` equals the `did` of a card the
origin serves that is not excluded under §4. *(tests: "a handoff to the DID the card names…",
"ATTACK: a handoff is not vouched for by a card that fails its signature")*

**AWR-15.** An entry naming no `to` and any URL off the dialled origin (and off the origin the
card's `url` names) MUST be refused. *(test: "a ui continuation on the origin is accepted but
flagged…")*

**AWR-16.** A `ui` entry MUST NOT be opened without `person` on hand; an implementation MUST
mark it as requiring a person. *(same test)*

## 7. Out of scope

Minting a key, signing, and delivering the message to the door are not specified here. The
router MAY return the door's own description of the message it accepts (from the card's
`securitySchemes`) for the component that holds the key.

## 8. Conformance

An implementation conforms when the tests named above pass against it. The reference
implementation is `agent-web-router.mjs` in this repository; `npm test` runs the suite
against a local site fixture that signs its own card with its own independent canonicalizer.
